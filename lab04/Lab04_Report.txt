1. The Deadlock (Phase 2):
In the 'deadlock_simulation.py' script, Circular Wait occurred through the following sequential steps:
1. Thread Model A requested and acquired 'gpu_0_lock', then called time.sleep(0.1), yielding the CPU.
2. The OS Scheduler switched context to Model B, which requested and acquired 'gpu_1_lock', then also slept.
3. Model A resumed and attempted to acquire 'gpu_1_lock', but blocked because Model B was holding it.
4. Model B resumed and attempted to acquire 'gpu_0_lock', but blocked because Model A was holding it.
5. This formed a circular chain of dependencies: Model A holds GPU 0 while waiting for GPU 1 held by Model B, and Model B holds GPU 1 while waiting for GPU 0 held by Model A. Since neither releases its acquired resource, both threads wait indefinitely in a Deadlock.

2. The Solution (Phase 3):
By forcing Model B to request 'gpu_0_lock' first (the same order as Model A), we enforce a strict Resource Hierarchy (Lock Ordering). Whichever thread acquires 'gpu_0_lock' first will proceed, while the other thread is immediately blocked at the very beginning before it can acquire any resource. This prevents the scenario where each thread holds one resource while waiting for the other, thus breaking the Circular Wait condition and eliminating the Deadlock.

3. Starvation vs Deadlock (Phase 4):
- Fundamental Difference: In Deadlock (Phase 2), the entire program freezes completely, with zero progress made across all threads, requiring manual OS termination (Ctrl+C). In Starvation (Phase 4), the system remains fully active and processes continue executing rapidly (Greedy models run thousands of times), but the Polite Model is indefinitely deprived of the shared resource due to unfair lock competition.
- Aging Technique: An OS process scheduler can implement 'Aging' by gradually incrementing the priority score of threads/processes the longer they spend waiting in the ready queue. Eventually, the priority of 'Polite_Model' will surpass the priority of 'Greedy' tasks, guaranteeing it scheduled access to the lock before priority drops back to baseline.

4. Deadlock Detection & Recovery (Phase 5):
- How the 'timeout' parameter simulated detection: The 'timeout=2.0' parameter defines a bounded waiting threshold. If the requested lock cannot be acquired within 2 seconds, the lock acquisition fails and returns False. This simulates an OS watchdog timer or deadlock detector identifying that a thread has stalled in a wait-state past an acceptable duration.
- Model A's Recovery Step: Once the timeout expired, Model A executed an automatic recovery/rollback procedure by calling 'gpu_0_lock.release()', yielding its held resource back to the system. This allowed the waiting Model B to acquire GPU 0, complete its execution, and prevent a permanent system freeze.

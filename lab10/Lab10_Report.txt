  [Explain how the OS prevented Thrashing by using the `while` loop for RAM allocation]

- Concurrency & Deadlocks (Labs 3/4):
  [Explain how the OS sorted the requested GPUs to avoid Circular Wait deadlocks]

  การแก้ปัญหา Deadlock: เป็นการประยุกต์ใช้กฎ Resource Ordering (Resource Hierarchy) เพื่อทำลายเงื่อนไข "Circular Wait" (การรอคอยแบบวงกลม) เช่น แม้ว่า Workload A จะส่งรายการ GPU เข้ามาเป็น [2, 1, 0] แต่ระบบจะจัดเรียงใหม่ให้จอง GPU 0 ก่อน ตามด้วย 1 และ 2 เสมอ ทำให้ไม่มีกรณีที่สองโปรเซสต่างถือ GPU คนละตัวแล้วรอสลับกันจนระบบค้างแบบ Deadlock

2. Hardware Utilization:
Look at the output of your Live Dashboard. Explain how the OS successfully ran Workload A (LLaMA Training), Workload B (Preprocessing), and Workload C (Inference) AT THE SAME TIME without crashing. Why didn't they block each other?

Answer:
โปรเซสทั้งสามสามารถทำงานพร้อมกันได้ (Parallel / Concurrent Execution) อย่างราบรื่นและไม่เกิดการบล็อกกัน เพราะระบบปฏิบัติการบริหารและจับคู่ทรัพยากรตาม Resource Requirements ที่ต่างกันได้อย่างลงตัว:
1. การจัดสรร RAM: ความต้องการ RAM รวมของทั้ง 3 งานคือ 40GB (A) + 16GB (B) + 2GB (C) = 58GB ซึ่งไม่เกินขีดจำกัดความจุรวมของระบบ (Total 64GB) ทำให้ทุกงานได้รับการ Allocate หน่วยความจำพร้อมกันได้โดยไม่ต้องรอ
2. การจัดสรร GPU โดยไม่ขัดแย้งกัน:
   - Workload A (Distributed Training) จองใช้ GPU 0, 1, 2
   - Workload B (Data Preprocessing) เป็นงานฝั่ง CPU-Bound / I/O-Bound ที่ไม่ใช้ GPU เลย (`req_gpus=[]`) จึงแทรกตัวทำงานบน CPU ขนานไปกับ A ได้ทันที
   - Workload C (Inference API) ใช้เพียง 1 GPU ระบบจึงฉวยโอกาสส่งเข้าไปรันบน GPU 3 ซึ่งว่างอยู่พอดี
ส่งผลให้ระบบสามารถดึงทรัพยากรทั้ง CPU, GPU และ RAM มาใช้งานได้อย่างเต็มประสิทธิภาพสูงสุด (Hardware Utilization) พร้อมกันโดยไม่มีงานใดติดขัด

2. I/O Bound Concept:
If an Operating System is described as being "I/O Bound" during a task, what does that actually mean for the CPU? Is the CPU at 100% usage
 or is it mostly idle? Why?

Answer:
- สภาพของ CPU เมื่อเกิด I/O Bound:
CPU จะ "ไม่ได้ทำงาน 100%" แต่จะอยู่ในสภาพ "ว่างงานเป็นส่วนใหญ่ (Mostly Idle หรือเกิดอาการ I/O Wait สูง)" 

- เหตุผลตามความเข้าใจของผม:
เพราะว่าคอขวดของงานอยู่ที่ความเร็วในการอ่านเขียนข้อมูลบน Storage/Disk ซึ่งทำงานช้ากว่า CPU มหาศาล 
เมื่อโปรแกรมส่งคำสั่งขอข้อมูลไป ตัวโปรเซสจะต้องถูกเปลี่ยนสถานะไปเป็น Waiting State เพื่อรอให้ดิสก์อ่านข้อมูลเสร็จแล้วส่งเข้ามาที่ RAM เสียก่อน 
ระหว่างที่รอข้อมูลส่งมา CPU ไม่มีคำสั่งอะไรให้ประมวลผลต่อ จึงต้องนั่งว่างงานรอคอย Disk I/O อยู่เฉยๆ

3. AI Industry Connection (Phase 3):
Explain why storing an AI image dataset as 1,000,000 separate `.jpg` files causes high I/O overhead and GPU starvation 
compared to packing them into a single sequential binary format (e.g., TFRecord, WebDataset, or HDF5).

Answer:
- ปัญหาจากการเก็บ 1,000,000 ไฟล์แยก (Random I/O):
ทำให้ระบบปฏิบัติการเกิด OS Overhead มหาศาล เพราะต้องคอยเรียก System Calls คำสั่ง open, read, close ซ้ำๆ กันเป็นล้านรอบ อีกทั้งต้องคอยค้นหาตำแหน่ง Inode, 
 Permission และหัวอ่านดิสก์ต้องวิ่งสุ่มหาบล็อกไฟล์ที่กระจายอยู่ทั่ว ส่งผลให้อ่านข้อมูลได้ช้ามาก จนเกิดภาวะ "GPU Starvation" คือการ์ดจอคำนวณรอบเดิมเสร็จแล้ว 
 แต่นั่งว่างงาน (Usage ตกเหลือ 0%) เพราะดิสก์ส่งภาพรอบใหม่เข้ามาป้อนไม่ทัน

- ทำไมรวมเป็นไฟล์ก้อนเดียว (Sequential Binary) ถึงดีกว่า:
จากการรัน `ai_dataset_io.py` เห็นได้ชัดเจนมากว่า การอ่านไฟล์ย่อย 1,000 ไฟล์ใช้เวลาถึง 0.0217 วินาที แต่พอรวมเป็นไฟล์ก้อนเดียวแบบ 
TFRecord ใช้เวลาเพียง 0.0024 วินาที (เร็วขึ้นเกือบ 10 เท่า) เพราะระบบเปิดไฟล์เพียงแค่ครั้งเดียวแล้วสตรีมข้อมูลอ่านต่อเนื่องตามขนาดบล็อกได้ทันที 
ช่วยลดการเรียก System Calls และลดเวลา Seek Time ของดิสก์ ทำให้ Data Pipeline ป้อนข้อมูลเข้า RAM และ GPU ได้ไหลลื่น ไม่ปล่อยให้ GPU ต้องนั่งว่างงาน
